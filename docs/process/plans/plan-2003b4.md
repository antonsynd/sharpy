# P21a — Stage 1 of the declaration keyword model: the `let` keyword (additive, ungated)

## Context

Issue **#1974** (owner design, ruled 2026-09-21/22) replaces Sharpy's keywordless declaration model
with one binding law: **`let <target> = e` introduces a fresh block-scoped mutable binding; bare
`<target> = e` writes through to the nearest existing binding; `const NAME[: T] = e` is
assign-once; module scope is `const`-only; `auto` is retired.** The round charter
(`.claude/plans/remediation-round-2026-09-20-batching.md` §3.9c, rulings R-BI…R-BM) splits the
work into three sub-phases, each its own plan and measured gate: **21a Stage 1 (this plan)** →
21b codemod + migration → 21c Stage 2 (the breaking flip). R-BI orders P21 after P20 and P18b;
the owner has explicitly pulled 21a forward ("we churn a lot on the other things, and at that rate,
we will never get to this") — recorded under `## Scope › Override`.

**What 21a delivers** (charter §3.9c, "21a — Stage 1", verbatim contract): `let` becomes an
unconditional keyword (R-BJ: no feature flag); the parser accepts `let <target>[: T] = e` with
single and tuple targets; the checker's introduce-vs-write-through trigger reads `let` (a `let`
target is *always* a fresh binding, even when a same-name binding exists in the same scope, an
enclosing block, the enclosing function, or the module); annotated bare `x: T = e` still declares
and bare `x = e` still declares-if-new (Stage 1 is additive); `:=` is unchanged (R-BK); `let` at
module scope and in a type body is refused (SPY0340 with the `const` steer per R-BL; type bodies
get the field steer); `out let x` introduces while `out x` and `out x: T` keep today's behaviour
(R-BM). Spec files are updated and every fenced block they contain compiles or carries a marker,
with each file's `spec_blocks_allowlist.txt` rows drained first (R-BG standing rule).

**What 21a does NOT do** (ruled for 21b/21c — do not pull forward): no corpus migration (21b),
no `auto` removal or SPY0240 retirement (21c), no SPY0611 (21c), no `var`/`val` reservation (not
in any ruling), no change to what bare `=` or `x: T = e` mean in a function body (21c).

Rulings are authoritative and posted on #1974 (comment
https://github.com/antonsynd/sharpy/issues/1974#issuecomment-5779904323 and the three owner
comments before it). Do not re-ask A–D, C, R-BI…R-BM.

## Design Decisions

1. **AST shape: `let` is a flag on the two existing store nodes, not a new node** (rung 4 —
   syntax; the lower rungs cannot carry a keyword). `let x = e`, `let a, b = e`, `let first, *rest
   = e` parse to `Assignment { IsLet = true, Operator = Assign }` (identifier / tuple / starred
   targets, canonicalised by `AstHelper.CanonicalizeStoreTarget` exactly as today); `let x: T = e`
   parses to `VariableDeclaration { IsLet = true, Type = T, InitialValue = e }`; `out let x[: T]`
   parses to `ModifiedArgument { InlineName, InlineType = T | null, IsLet = true }`. Rationale:
   (a) the emitter then needs NO change — the unannotated `let` rides the Assignment-Declares arm
   (`TargetBinding.Kind == Declares` → `LocalDeclarationType` → `var x = …`), which is the
   arm today's declaring `x = e` already uses, so `let x = e` ≡ `x = e` in emitted C# *by
   construction* (21b's output-invariance acceptance depends on this); (b) tuple/star targets reuse
   the unpacking machinery `VariableDeclaration` lacks; (c) a new node would need an arm in every
   visitor (`AstVisitor` and `AstVisitor<T>` subclasses, `AstNormalizer`, `StructuralEqualityComparer`,
   `AstFingerprint`, CFG, DA, 12 validators, 5 LSP handlers, the emitter) — the parallel-site
   class in one commit. Cost accepted: two nodes carry the flag, and `IsLet` must be compared in
   `StructuralEqualityComparer`, `AstFingerprint` and printed by `UnparseVisitor` on both.
   `let` sets the statement's `LineStart/ColumnStart` to the `let` token (like `const`); the
   target/name keeps its own position (LSP `EffectiveNameLine/Column` reads the name).
2. **One introduce seam in the checker.** A new private helper
   `StatementStorePredecessor(string name, bool isNameBacktickEscaped, bool introduces)` in
   `TypeChecker` returns the predecessor `VariableSymbol?` (`existingSymbol ?? parentSymbol`, the
   rule spelled inline at THREE sites today — `CheckAssignment`'s identifier arm
   `Statements.cs:178/286`, `CheckTupleUnpackingElements`' inline binder `Patterns.cs:1647`, and
   `BindAssignmentUnpackingIdentifier` `Unpacking.cs:268`) or `null` when `introduces` is true. All
   three call it with `introduces: assignment.IsLet`, threaded through
   `CheckTupleUnpackingElements` (non-star tuples, literal and typed RHS) and
   `CheckUnpackingTargets` (star tuples) as a parameter (default `false` for the non-assignment
   positions — `for`, `with`, comprehension targets keep their own introducers) [CORRECTED: the
   plan named two sites; `Patterns.cs:1624–1790` is the third and is the one `let a, b = 1, 2`
   reaches]. The SPY0606 refusal is gated on `!introduces` at its two statement-store call sites
   (`Statements.cs:59` plain prelude, `Patterns.cs:1639` tuple element) — a `let` target is the
   explicit new local the steer recommends, exactly as the annotated form already bypasses it. The expression seam `ExpressionRebindingPredecessor` gains
   the same `introduces` gate for `out let`. 21c flips the bare case INSIDE this helper (predecessor
   `null` on a bare store → SPY0611), so the Stage 2 change is one arm, not five.
   `SetRebindingPredecessor` is not called for a `let` binding: it is a fresh chain root, and
   `LocalNameAllocator` versions it (`x_1`) exactly as it versions an annotated shadow today
   (`variable_scoping.md` "Implementation" note stays true).
3. **`let` keeps every refusal the annotated declaration has.** Same-scope `const` of the same
   name → SPY0225 "Cannot redefine constant variable" (mirrors `CheckVariableDeclaration:1109`);
   a hoisted def/class of the same name → `TryReportNonVariableRedefinition` (SPY0204); an OUTER
   const (module `const X`) is shadowed by a function-body `let X` exactly as `X: int = 1` shadows
   it today (measured behaviour of the annotated form; a matrix cell, not a new rule). A class
   attribute named like the `let` target inside a method: `let count = 1` AND `let count, other =
   1, 2` are the explicit "new local" — SPY0606 does NOT fire at either call site (it fires for the
   bare `count = 1` and bare `count, other = 1, 2` controls, both measured @ 05824d52f; #1974 §4
   "clarity win"), and SPY0606's steer gains `'let count = ...'` as the first suggestion
   [CORRECTED: tuple-element site named].
4. **Two position refusals, one seam each.** Module: `ModuleLevelValidator` gets a `let` arm
   (`Assignment { IsLet: true }` and `VariableDeclaration { IsLet: true }`) placed BEFORE the
   `VariableDeclaration` untyped check, reporting SPY0340 with the R-BL steer: "`let` declares a
   local binding and is not allowed at module level; module-scope bindings are `const`: use
   'const NAME[: T] = ...'". Type bodies: a new `TypeBodyStatementValidator : ValidatingAstWalker` (new; `ValidatingAstWalker` is the `AstVisitor`-based validator base in `Semantic/Validation/ValidatingAstWalker.cs`)
   (Order 51, beside `ModuleLevelValidator`) visits `ClassDef`/`StructDef`/`InterfaceDef`/`UnionDef`
   bodies through ONE `ClassifyTypeBodyStatement(Statement, hostKind)` and refuses the two `let`
   shapes with SPY0340 and the field steer: "`let` is not allowed in a class body; declare a field
   as 'x: T = ...' or a constant as 'const X = ...'". **Assumption (owner may override at
   `/batch-issues`):** SPY0340 is reused for the type-body cell rather than allocating a code
   (R-BL rules "one new code" for P21 and its explanation is generalised to "declaration-only
   positions"). The validator is deliberately the seam where the outside-contract SPY0510 class
   (executable statements in a type body, p3/p17–p19) will later be cured by adding arms — 21a
   adds only the `let` arms and records the rest in the findings ledger. The `NameResolver`
   class/struct loops additionally skip a `VariableDeclaration { IsLet: true }` so a refused `let`
   never registers as a field (otherwise the SPY0340 site would also produce a field symbol and
   downstream noise). Why "exactly one diagnostic" is reachable [ADDED: verifier probe e @
   05824d52f]: `ProjectCompiler` skips code generation once `_diagnostics.HasErrors`, so the
   emitter's SPY0510 `default:` arm is unreachable after SPY0340 fires (a class-body `print(1)`
   beside an SPY0220 reports only SPY0220). The TypeChecker's class-body loop
   (`TypeChecker.Definitions.cs:1229` `CheckStatement`) still visits the refused node; the
   `DiagnosticCount == 1` assertion is what proves it adds nothing.
5. **Parser: recognise `let` inside `ParseSimpleStatement`.** On `Current.Type == TokenType.Let`
   the method advances, parses the target with the existing target/tuple/star machinery, then
   requires exactly one of `: T = e` (single identifier target only) or `= e`; anything else is a
   named refusal under existing parser codes: no initializer → SPY0104 "`let` requires an
   initializer ('let x = ...')"; augmented operator → SPY0100 "`let` takes '=' only"; member /
   index target → the existing target-shape code with "`let` target must be a name or a tuple of
   names". Because the three dispatchers all end in `ParseSimpleStatement`, `@suppress(...) let x =
   e` and inline `defer let x = e` work without a new arm; `@static let x = 1` keeps SPY0105
   (decorators apply to fields, and a `let` is not a field). `IsSyncToken` and `IsKeywordToken`
   gain `Let` (error recovery; `obj.let` member access by keyword-as-name). Two more cells
   [ADDED: verifier]: `let.x = 5` is claimed by the keyword-qualifier rule at `Parser.cs:798`
   BEFORE `ParseSimpleStatement` sees a `Let` token — it stays SPY0200 (identifier `let`), asserted
   so the cell is deliberate; `ref let x` / `in let x` inside a call → a named refusal (the
   `ModifiedArgument` invariant `IsLet ⇒ Modifier == Out` must be refused by the parser, never
   asserted at runtime).
6. **Inline `out let`** (R-BM): `out let x` is a fresh binding whose type flows from the callee
   (`InlineType == null` ⇒ `resolvedType = Unknown` ⇒ the existing `WriteBackAutoOutBindingType` /
   `RefuseUnresolvedAutoOutBindings` path, keyed on `UnknownType`, not on the name `auto`);
   `out let x: T` is fresh with an explicit type. `out x` and `out x: T` are byte-for-byte
   unchanged in 21a. The emitter's inline-out arm maps `InlineType == null` to `var` (a structural
   check beside the pre-existing `Name == "auto"` string check, which 21c deletes). The
   `ValidateInvariants` assertion becomes `InlineType != null || IsLet`.
7. **Spec is authoritative and describes Stage 1 honestly.** The declaration sections say: `let`
   introduces; `const` is assign-once; bare `x = e` on a new name and annotated `x: T = e` still
   declare **in Stage 1** (a transitional sentence citing #1974 Stage 2, so the codemod in 21b and
   the flip in 21c edit one sentence each); `auto` is documented as deprecated in favour of `let`
   (retired in Stage 2). `statements.md:176`'s "compile-time constant initializer" is corrected to
   "an initializer; a compile-time constant lowers to C# `const`, anything else to `static
   readonly`" (owner-measured, `decorators.md:274`). Every example is executed against HEAD before
   commit and prefers discriminating outputs (a shadow example prints a value the write-through
   reading would not).
8. **No feature flag** (R-BJ); no `TransitionWarningValidator` warning for keywordless declarations
   (21b's codemod is the migration instrument; a warning is not ruled and would fire on the entire
   corpus).
